# 04. Протокол измерений

Без этого документа «эффективность на стандартном железе» — разговор о вере.
Ниже — минимум, при котором число в README считается существующим.

## 0. Определения (чтобы не спорить)

- `B_tok` — байт, читаемых из памяти на генерацию одного токена
  (`= N_act·b + L·c_kv + 1.15·служебное`). Считается аналитически по конфигу модели.
- `tok/s` — скорость decode (не prefill!) при указанном батче; prefill сообщается отдельно.
- `E_tok` [Дж/токен] = `P_avg / tok/s`, где `P_avg` — средняя потреблённая мощность
  за интервал измерения (только под нагрузкой, без простоя «на прогрев»).
- `E_task` [Дж/задача] = Σ(E_tok × токенов) + энергия предзаполнения + энергия адаптации
  (если в этой сессии был шаг обучения/сна, он сюда включается — это принципиально).
- `Ψ` = ΔКачество / `E_task`.
- `Качество` — доля решённых задач вашего доменного набора; MMLU не принимается.
- Всё, что зависит от длины входа (ток/с, Э_задача), сообщается **вместе с L**.

## 1. Отбор мощности (три источника, в порядке доверия)

1. **Счётчик в розетке** (PAD-ваттметр, лог с 1 Гц). Абсолютно честно, включает всё:
   блоки питания, вентиляторы, потери. Для «20 Вт vs датацентр» вопросов — единственный
   корректный источник.
2. **RAPL** (Linux): `/sys/class/powercap/intel-rapl:0/energy_uj`, `/sys/fs/cgroup` — CPU+PKG
   (не включает дискретный GPU).
3. **NVML**: `nvidia-smi --query-gpu=power.draw,utilization.gpu,memory.used,clocks_throttle_reasons.active -l 0.2`.
   Учитывать: `power.draw` — мгновенное, интеграция по 5 Гц-выборке; частота опроса ниже
   10 Гц на коротких прогонах врёт сильнее 10%.

Правила: прогон ≥60 с (короче — доминирует шум опроса); предварительный прогрев 120 с;
фон выключен (`docker stop`, браузеры, строка поиска); лимит мощности зафиксирован и записан;
термо-троттлинг проверен по `clocks_throttle_reasons.active` — если троттлит, результат
помечается `thermal=true` и не сравнивается с нетроттлящими.

## 2. Протоколы

### B1. Сквозная эффективность инференса (базовый, обязательный перед/после любой правки)
```
матрица: {квант} × {ctx ∈ 2k,8k,32k,128k} × {tg=256, decode-only}
повторы: 3; отчёт: медиана и размах; плюс B_tok(аналитика) — сверка модели с реальностью
выход:   строка в out/runs.jsonl
```
Ожидаемое (для самопроверки стенда): `tok/s ≈ 0.65·BW / B_tok` с точностью ±25%.
Если расхождение >2× — у вас не «уникальная оптимизация», у вас сломан измеритель
(обычно: батч>1, k-кэш не в том формате, PCIe-узкое место, CPU-bound sampler).

### B2. Энергия на задачу (главная таблица проекта)
```
набор: ≥300 доменных задач с автотестом/верификатором
конфигурации: базовая | +A3(кэш) | +A3+A1 | +каскад | +каскад+MTP
метрики: доля решённых, Э_задача, пик RAM, латентность p50/p95
критерий принятия: Δрешаемость ≥ −2 п.п. при ≥1.5× снижении Э_задача
```

### B3. Обучение/консолидация (E2, E1)
```
3 сида; метрики: валид. ppl, Дж на шаг, пик памяти, время до целевой ppl
плюс регресс-набор (≥200 задач) до/после вшивания адаптера; откат при −>1 п.п.
обязательно: контрфакт «с артефактом / без» для каждого записанного скилла
```

### B4. Длинный контекст (там, где «архитектура» и проявляется)
```
ctx: 8k → 1M (или максимум модели); фикс. задача NIAH-многосвязная + агентская сессия
фиксируем: KB чтения/токен на состояние; деградация tok/с к 32k/128k (в %)
```
Это тот протокол, на котором A4 (гибридное внимание) доказывается или умирает.
