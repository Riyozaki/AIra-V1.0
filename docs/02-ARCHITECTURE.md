# 02. Архитектура AIra: стек, а не модель

Принцип: модель — это один из слоёв. Интеллект на ватт живёт в **политике
что/где/когда считать**. Все числа ниже — проектные цели, а не обещания; каждая
строка обязана быть измерена по `docs/04-BENCH.md`.

```
                       ┌──────────────────────────────────────────────┐
  запрос ──► НОРМАЛИЗАТОР ──► GATE (кто решает) ──► ИСПОЛНИТЕЛЬ ──► ПИСАТЕЛЬ ПАМЯТИ
                       │                                   │
                 кэш префиксов                       базовая 3–4B (Q4/тернарная)
                 + скилл-индекс                      эскалация → 35B-A3B / внешний сервер
                                                     «сон» → LoRA-оверлей (ночью)
```

## 1. Каскад (главный множитель по энергии)

| Ступень | Модель | Формат | Назначение | Бюджет |
|---|---|---|---|---|
| S0 | 0.5–1B (свой дистиллят или BitNet-2B) | IQ2 / 1.58-bit, CPU | роутинг, извлечение сущностей, «это вообще не про меня» | ≤0.05 Дж/токен |
| S1 | 3–4B, домен-дистиллят | Q4, CPU или dGPU | 70–85% задач, tool-форматирование | ≤0.3 Дж/токен |
| S2 | 30–40B MoE, A3–A4B | Q4/IQ3, unified mem | рассуждение, код, план | ≤3 Дж/токен |
| S3 | внешний frontier API | — | <3% задач, где цена ошибки высокая | деньги вместо джоулей |

Правила эскалации (жёсткие, чтобы каскад не превратился в лотерею):
1. S1 отвечает «не знаю» или генерирует invalid tool-JSON → эскалация один раз, без циклов.
2. Средняя длина «думания» S1 > порога → эскалация с передачей черновика (не с нуля).
3. Эскалация не более 1× на запрос; стоимость каскада = `J_S1 + p·J_S2`, и она обязана
   быть посчитана в логе (см. `tools/aira_calc.py cascade`).

Почему это «обход», а не костыль: датацентр берёт эффективностью *батча*, вы берёте
эффективностью *пропущенных токенов*. Математически это одно и то же неравенство,
но у вас в знаменателе стоит 20 Вт, а не 700.

## 2. Базовая модель: что именно строить

Ставка (обоснована в `01-LEVERS.md`, A1/A2/A4/B1/B2):

- **Архитектура:** гибридная, 3:1 линейно-рекуррентные слои (KDA/GDN-класс) : полное
  внимание (MLA-стиль латентного KV), **NoPE** в глобальных слоях; MoE 64–256 экспертов,
  8 маршрутизируемых + 1 общий, aux-loss-free балансировка; FFN ReLU²; value embeddings;
  0.8–4B активных, 8–40B общих.
- **Почему так, а не «с нуля своё»:** это единственная конфигурация 2025–2026, для которой
  есть (а) открытые чекпойнты-учителя того же класса, (б) работающие кернели в vLLM/llama.cpp,
  (в) измеренные обещания −75% KV и 6× decode на длинном контексте. Ваша свобода —
  не изобретать слой, а выбрать *бюджет* и *данные*, и добавить один собственный механизм.
- **Тернарный вариант (для 20-Вт-ветки):** если целевой носитель CPU/SoC — учить сразу
  BitLinear-вариант (absmean-квантизация весов, 8-bit активации), а не квантовать потом.
- **Чего явно нет в стеке:** свой токенизатор (экономия сомнительная, риски реальные),
  свой distributed-фреймворк, свой «оптимизатор». Только Muon+AdamW на не-2D,
  WSD-расписание LR, градиентная отсечка 1.0.

**Порядок сборки (важно, чтобы не умереть на инфраструктуре):**
1. Взять готовый чекпойнт учителя того же семейства и *не* учить с нуля.
2. Собрать корпус домена (промпты из реальных рабочих сессий + синтетика + верификация).
3. On-policy distillation (reverse-KL) до плато; параллельно — 1–2 прогона RLVR
   только на проверяемых подзадачах.
4. QAT/квантизация под целевой носитель.
5. Только после этого — архитектурный эксперимент (пункт C1) на том же конвейере,
   чтобы сравнение было честным «яблок к яблокам».

## 3. Память: три подложки и один бюджет

```
уровень 0  KV/prefix-кэш            цена ≈ 0        жизнь: сессия      удаление: LRU/TTL
уровень 1  артефакты (скилл-файлы,  цена ≈ 0 GPU    жизнь: месяцы      удаление: по провалу
           правила, примеры-эталоны)                 (текст, git-версионируется)
уровень 2  LoRA-оверлей «сна»        цена: 10–120    жизнь: до отката   удаление: версия+1,
                                    минут на 1 GPU                     откат по регрессии
уровень 3  переобучение весов        недоступно      —                  —
```

Уже занято другими (цитировать обязательно): Letta sleep-time compute / dreaming;
`sleeping-llm` (MEMIT-впрыск + ночной LoRA-fuse, откат по перплексии, 3B на MacBook Air M3);
LightMem; Mem0/LongMemEval/BEAM/LoCoMo как бенчмарки; MemoryBench, SkillLearnBench,
AFTER — как датасеты процедурной памяти. Их общий провал, и ваше окно:
**автономно выученные скиллы дают ~30% против ~74% у написанных человеком**
(SkillLearnBench, 2026). Значить цель — не «память вообще», а *качество записи* и
её цена.

## 4. Политика записи — формализация (то, что мы реально предлагаем)

Для каждого кандидата `c` (фрагмент диалога, неудачный tool-call, новое правило, паттерн
ошибки) в момент `t` система оценивает **полезность размещения на подложке `l`**:

```
score(c,l) =  R(c) · Δq(l)  −  λ_e·E_write(l)/Task_budget  −  λ_r·Risk(l)  −  λ_o·Occupancy(l)

R(c)   — ожидаемая частота переиспользования (оценка: экспоненциальное сглаживание
         по успешным возвратам к этому фрагменту;старт: 1/(1+Δt))
Δq(l)  — прирост вероятности успеха, измеренный контрфактом: прогон с артефактом vs без
         (единственный источник правды; не «по ощущению»)
E_write— энергия записи (0 для кэша/текста; минуты GPU-времени для адаптера)
Risk   — вероятность интерференции: Δ на фикс. регресс-наборе после вшивания
Occ    — занимаемое место в дефицитном ресурсе (VRAM/контекст)
```

Правило: пишем на самую дешёвую подложку, где `score > 0`, и **периодически понижаем**
(артефакт, который 30 дней не возвращался, уходит в архив; правило, давшее регрессию
на фазе «сна», откатывается версией). Это ровно то, что в нейроновом описании зовётся
консолидацией и «управлением допуска», но записано как задача оптимизации с явной
стоимостью энергии — и это делает её проверяемой и публикуемой.

Метрика качества всей системы (целевая функция проекта):

```
Ψ = ΔУспех(доля решённых задач) / (Э_инференс + Э_адаптация + Э_запись)   [1/Джоуль]
```

Всё, что не двигает `Ψ`, в стек не входит.

## 5. Инференс-контур: что включено по умолчанию

```bash
# llama.cpp-ветка (CPU/unified) — базовая конфигурация для «всегда он»
llama-server -m <model>.gguf \
  --cache-type-k q8_0 --cache-type-v q8_0 \
  --flash-attn on --parallel 1 \
  -c 131072 --cache-ram 16384 --cache-reuse 8 \
  --cpu-moe --ncmoe <k_from_scan> \
  --spec-type draft-mtp --spec-draft-n-max 2 --reasoning auto
```

- `--cpu-moe`/`-ncmoe` — эксперты в RAM: берём из A2, k по скану, не по догадке.
- KV в q8_0 (или q4 для «холодных» сегментов) — обязательно: на 128K это ×2–×4 полос.
- `draft-mtp` — только при acceptance ≥0.5, иначе выключить и записать в журнал почему.
- Префикс-кэш + `--cache-reuse` — структурное требование к промпту: **инвариантный
  префикс** (система + скиллы) сначала, изменчивое (история, файлы) потом. Порядок секций
  промпта — это не косметика, это 5–30×.
- Никакого «resummarize всё каждый ход»: резюмирование — функция порога (KV > X ГБ
  или промах по кэшу), иначе вы платите предзаполнением за иллюзию экономии.

## 6. Отказоустойчивость и безопасность стека

- Каждое вшивание адаптера — с версией и авто-откатом по регресс-набору (≥200 задач).
- Никакой автозаписи в уровень 1/2 из «сомнительных» источников: промпт-инъекция,
  приехавшая из веба, не должна уметь становиться правилом. Правила, полученные из
  внешнего контента, проходят карантин (1 сессия в роли «предложение»).
- Любая эскалация на S3 (внешний API) — явный лог, потому что это и утечка, и деньги.
- Все числа в README/отчётах имеют ссылку на лог; нет лога — нет числа (см. `04-BENCH.md`).

## 7. Что мы сознательно НЕ делаем

- Не соревнуемся в предобучении (>10B токенов с нуля — нет).
- Не пишем свой фреймворк обучения: берём nanochat/modded-nanogpt как стенд,
  llama-factory/unsloth/TRL/verl — как пост-тренинг.
- Не строим «AGI на 4090». Строим: узкий домен, локально, измеряемо, ×5 по энергии,
  с одним архитектурным вкладом и одним алгоритмическим (политика записи).
